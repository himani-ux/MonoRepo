# CR-163 - Planned Audit Lead Auditor Lock

**What & why** - When Register Audit is opened with registerable audit plans, the Lead Auditor fields should represent the auditor already assigned during planning. Leaving those fields editable lets users enter values that the backend later overwrites from the selected plan, creating confusion and possible mismatch expectations.

**Tier + triggers** - Tier 2; changed screen state/behavior for the Register Audit form.

**Domains touched** - Step 1 Audit registration and Audit planning.

**Decisions** - No new SSOT decision. Existing planned-audit behavior is clarified: selected plan owns the lead-auditor snapshot during registration.

**Doc cascade** - `audit_docsuite/APP_FLOW.md` now states plan-backed registration carries the planned lead-auditor snapshot. `audit_docsuite/USER_GUIDE.md` now tells users the Lead Auditor fields are filled from the selected plan and read-only for planned audit registration. `audit_docsuite/TEST_PLAN.md` now covers the read-only lead-auditor behavior. Backend structure docs unchanged because no database table or endpoint path changed; only the plan response payload gained descriptive snapshot fields.

**Tests** - Added frontend registration-form coverage for selecting a plan, seeing the plan lead auditor in read-only fields, and submitting that snapshot. Added backend plan API assertion that plan list responses include the lead-auditor snapshot fields.

**Fidelity check** - No deltas. The implementation matches the intended planned-audit flow: the selected audit plan owns the lead auditor, the UI displays that auditor, and backend registration still overwrites from the plan as the authority.

**Exemptions** - none.
