**What & why**
Change the Audit Walk Checklist row status UI from a compact dropdown to radio-style choices so the auditor can mark each checklist item as Not reviewed, Compliant, or Findings without opening a select menu. The stored status values and finding creation behavior stay unchanged.

**Tier + triggers**
Tier 2 - small feature / behavior change. Trigger: changed screen state/control behavior on the existing Walk Checklist screen.

**Domains touched**
Audit checklist walk: `FEAT-AUD-301`, `SCR-AUD-3`.
Audit finding capture: `FEAT-AUD-302`.

**Decisions**
Accepted default: keep existing stored values `NOT_REVIEWED`, `COMPLIANT`, and `ADD_FINDING` to avoid API or database changes.
Accepted default: display the third choice as `Findings` while preserving the existing `ADD_FINDING` status that enables the Add Finding action.
Accepted default: interpret the requested `complaint` label as `Compliant`, matching the current audit status value and checklist documentation.

**Doc cascade**
- `audit_docsuite/USER_GUIDE.md` - Walk Checklist instructions now describe radio-style item status choices.
- `audit_docsuite/TEST_PLAN.md` - Checklist walk regression now expects radio status choices instead of a dropdown.
- `Docs/progress.txt` - Maintain ledger entry appended.
- `audit_docsuite/APP_FLOW.md` - unchanged because it already documents checklist completion conceptually, not the row input control type.
- `audit_docsuite/BACKEND_STRUCTURE.md` - unchanged because no backend contract changes.

**Tests**
- `npm test -- "src/routes/audit/audits/[auditId].checklist.test.tsx"`
- `npm run type-check`

**Fidelity check**
No deltas. `FEAT-AUD-301` / `SCR-AUD-3` require auditors to walk checklist items, and `FEAT-AUD-302` requires finding capture from checklist context. The change keeps the existing item status values and finding action behavior while making the status choice visible as radio options.

**Exemptions**
None.
