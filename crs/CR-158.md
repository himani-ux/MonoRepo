**What & why** - Audit registration currently allows the user to open "Register Audit" without a clear selected plan identity. When multiple confirmed plans exist for the same vessel, target and date alone are not enough to prevent selecting the wrong audit. This change adds an explicit selected-plan section to the registration screen using the existing audit plan list API, with a short plan reference, target, status, standards, and window shown before the user saves.

**Tier + triggers** - Tier 2. Triggers: changed Audit registration screen state, changed frontend registration selection behavior, and added frontend validation that requires a selected registerable plan when plan rows are available. No new endpoint, table, migration, role permission, external integration, or dependency is planned.

**Domains touched** - Step 1 domains: Audit registration; Audit plan/register; Audit frontend routing/navigation; Audit user guidance.

**Decisions** - D-MAINT-CR158: show confirmed/registerable audit plans in the Audit registration form as explicit selectable plan options. Use a derived short display reference from the existing `master_audit_plan.id`; do not add a new database column or numbering sequence.

**Doc cascade** - `audit_docsuite/APP_FLOW.md` updated to state that Register Audit shows a selected-plan identity before save. `audit_docsuite/USER_GUIDE.md` updated to instruct users to pick the correct plan by plan ref, target, standards, and window. `audit_docsuite/BACKEND_STRUCTURE.md` unchanged because the existing `GET /api/audit/plans/` and `audit_plan_id` contract are reused. `Docs/progress.txt` updated.

**Tests** - Added frontend regression coverage proving office Audit registration receives distinct same-vessel registerable plan options while excluding non-registerable rows, plus form coverage for the short plan reference/window label and submit block when no plan is selected.

**Fidelity check** - no deltas.

**Exemptions** - none.
