**What & why**
Certs list screens currently risk loading too much data in one request, which makes the UI feel buffered and slow. This change will make the affected fetch path incremental, returning an initial page quickly and allowing the frontend to load additional rows in smaller batches.

**Tier + triggers**
Tier 2 - small behavior change. Triggers: changed API query contract, changed screen loading state, and changed performance behavior for Certs list data.

**Domains touched**
Step 1 domains touched: Certs API, Certs frontend list screens, Certs documentation.

**Decisions**
No new SSOT decision. Accepted default: keep the existing `/api/certs/catalog/rows/` endpoint and response shape, add `page`/`pageSize` metadata, cap `pageSize` at 100, and have Catalog Admin render the first 50 rows before appending later pages in the background.

**Doc cascade**
- `certs_docsuite/APP_FLOW.md` - Catalog Admin now states that the first 50 rows load first and later pages append in the background.
- `certs_docsuite/BACKEND_STRUCTURE.md` - Catalog rows endpoint now documents `page`/`pageSize`, supported filters, the 100-row cap, and SQL `OFFSET/FETCH`.
- `certs_docsuite/FRONTEND_GUIDELINES.md` - Performance guidance now requires catalog admin paging instead of full-table client loading.
