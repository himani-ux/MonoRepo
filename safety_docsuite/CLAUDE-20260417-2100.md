## Safety-Specific Conventions

These conventions are **non-negotiable** and override any contradictory usage you may encounter in the SSOT (which contains historical drift from early sessions).

### Database naming

| Prefix | Purpose | Notes |
|--------|---------|-------|
| `vims_safety_*` | **Module-specific transactional tables** owned by Safety | NEVER use bare `safety_*`. The SSOT uses `safety_*` as historical drift — translate on every output. |
| `master_*` | **Shared reference / seed data** (DPA-maintained, consumed cross-module) | Seeded from `../safety-reference-data/` CSVs (174 M-SCAT rows, 52 immediate causes, 7 loss types, 329 SOI items) |

**Existing VIMS masters the Safety module consumes (do NOT duplicate):** `master_role`, `master_RoleByVessel`, `master_applied_rank`, `master_notification`.

If you see bare `safety_X` anywhere in SSOT or interrogation logs, classify it:
- Transactional / owned by Safety → `vims_safety_X`
- Reference / seed / cross-module consumable → `master_X` (drop the `safety_` infix when domain is clear; keep it for disambiguation, e.g. `master_safety_incident_type`)

### Feature IDs

- Format: `FEAT-SAF-<domain>-<NNN>` where `<NNN>` is 3-digit zero-padded.
- Domains: `INC` (Incident), `NM` (Near Miss), `SCM` (Safety Committee Meeting), `SOI` (Safety Officer Inspection), `XMOD` (cross-module contracts), `PDF` (PDF generation), `AUDIT` (audit trail / signatures / field history), `DASH` (dashboards / lessons-learned), `RBAC` (role-based access control).
- Examples: `FEAT-SAF-INC-001`, `FEAT-SAF-SOI-012`, `FEAT-SAF-XMOD-004`.

### Permission IDs

- **Form IDs:** `SAF_F_*` — e.g. `SAF_F_001` (Incident form), `SAF_F_002` (Near Miss), `SAF_F_003` (SCM), `SAF_F_004` (SOI).
- **Process IDs:** `SAF_P_*` — e.g. `SAF_P_001` (Create), `SAF_P_002` (Submit to office), `SAF_P_003` (Send back), `SAF_P_004` (Approve/Close).
- Stored in the shared `msc_profiles` auth chain — **Safety does not maintain its own permission table**. Mirror the Reporting module's `RPT_F_*` / `RPT_P_*` pattern.

### Component prefix

- All Safety React components begin with `Safety*` — e.g. `SafetyIncidentPhase3.tsx`, `SafetySoiChecklistRow.tsx`, `SafetyNearMissAnonymityBadge.tsx`.
- Shared sub-components live under `src/components/safety/shared/` (e.g. `SignatureBlock`, `AnonymityBadge`, `MScatPicker`, `BiasGuardChecklist`, `BarrierAnalysisCanvas`, `CausalLayerTabs`, `SoiFindingRow`).

### Django app + API

- **App path:** `apps/safety/` in the VIMS monorepo (mirror of `apps/reporting/`, `apps/inspection/`)
- **AppConfig name:** `apps.safety` registered in `INSTALLED_APPS`
- **URL mount:** `/api/safety/` via `config/urls.py` → `include('apps.safety.urls')`
- **API paths:** `/api/safety/incidents/`, `/api/safety/near-miss/`, `/api/safety/scm/`, `/api/safety/soi/`
- **Frontend routes:** `/safety/incidents/`, `/safety/near-miss/`, `/safety/scm/`, `/safety/soi/`

### DB connection

- **Connection name:** `ksm_marine_live` — **shared** with Reporting, Inspection, and platform.
- Safety does NOT use `eMarineSoft_live` (that is the legacy DB being migrated FROM).
- Safety does NOT create a new database.
- The Django DB router already knows `ksm_marine_live`; Safety models register in `apps/safety/models/` with no router changes.

## Locked Decisions Summary (Critical No-Go Rules)

These are the rules that, if violated, produce wrong software — not just style issues. Memorize them.

- **No "Acting-\*" concepts** (D-GAP-A3 / D-GAP-A4) — roles persist; the person in the role rotates via normal crew rotation. No "Acting-DPA", no "Acting-CO", no deputy chains, no MD-escalation logic. The universal escape valve is the timeline-extension procedure (D-GAP-B2).
- **Same-DB live joins, no ETL** (D-GAP-I2) — Safety lives in `ksm_marine_live` alongside Reporting / WRH / CMS / Purchase. No sync jobs, no staging, no staleness. Every cross-module lookup is a live JOIN.
- **No crypto in V1** (D-GAP-D2 / D-GAP-G2) — no hash chains, no legal-hold, no tamper-evident ledgers. Audit trails rely on append-only DB logs + RBAC, not cryptographic proof.
- **PMS decoupled** (D-GAP-I1) — Safety does NOT integrate with the PMS module in V1. No FKs to PMS tables. Cross-reference is manual only (text notes, links in comments).
- **Paper-first SOI has NO scan upload** (D-GAP-E4) — SOI workflow is: system generates checklist PDF/Excel with unique ID → user downloads → fieldwork done on paper → paper filed in ship SMS filing system → findings registered digitally linked via unique ID. There is **no upload column** and **no scan endpoint**. The paper IS the authoritative artifact.
- **"SOI Compliance %" label** (D-GAP-DESIGN-01) — the state pill is always "SOI Compliance %". Never "Inspection Compliance %". This is a cross-module disambiguation — the Inspection module owns the `Inspection Compliance %` label.
- **Near-miss reporter anonymity — DPA / FM only** (D-GAP-J1) — the near-miss reporter's identity is visible only to Designated Person Ashore (DPA) and Fleet Manager (FM). Hidden from Master, HOD, and all ship-side roles. Serializers must strip `reporter_id` / `reporter_name` / any PII-leaking field for non-DPA/FM audiences. Backend enforcement via `apps/safety/authentication/anonymity.py`.

## Self-Improvement Loop

After every correction or bug fix:

1. Identify what went wrong.
2. Identify why (root cause).
3. Write a rule that prevents it.
4. Add to `LESSONS.md` with format: `L-NNN — <What> | <Why> | <Rule>`.
5. Continue.

Review `LESSONS.md` at every session startup. The loop is only valuable if it's read.

## Autonomous Bug Fixing

When encountering a test failure or bug:

1. Read the error message completely.
2. Identify the failing component.
3. Check `LESSONS.md` for known patterns.
4. Fix the root cause (not the symptom).
5. Run the test again.
6. If fixed: add to `LESSONS.md` if it's a pattern.
7. If not fixed: try a different approach (max 3 attempts).
8. If still failing after 3 attempts: escalate to Prince with full context — what failed, what you tried, why each attempt failed, your best hypothesis.
