# Backend Overview

## 1. Backend Architecture

The backend is a Django project that behaves as a modular API platform.

Primary responsibilities:

- authenticate users without Django `auth_user`
- enforce role and vessel scoping
- expose PSC inspection/CAR/sync APIs
- preserve legacy Circular and ORB APIs
- generate exports and report files

## 3. Core Settings

### 3.1 Important Settings

- `INSTALLED_APPS` includes PSC apps plus legacy Circular and ORB apps
- `REST_FRAMEWORK` uses a custom JWT authentication class
- `CORS_ALLOWED_ORIGINS` is environment-driven
- `MEDIA_ROOT` stores report uploads and company logo files
- `UPLOAD_BASE_PATH` controls the user-upload folder used for evidence and inspection reports

### 3.2 Database Settings

The backend uses SQL Server via `mssql-django` and `pyodbc`. The current codebase expects a shared schema rather than a brand-new autogenerated database.

## 4. Middleware

Configured middleware includes:

- `corsheaders.middleware.CorsMiddleware`
- Django security middleware
- session middleware
- common middleware
- CSRF middleware
- authentication middleware
- message middleware
- clickjacking protection

The most important ordering rule is that CORS middleware appears before common middleware so preflight requests are handled correctly.

## 5. Authentication Flow

### 5.1 Login

1. The frontend submits username and password to `POST /api/psc/auth/login/`.
2. `PSCAuthenticationBackend` tries vessel authentication first.
3. If vessel auth fails, it tries office authentication.
4. On success, the backend returns access token, refresh token, and a normalized user payload.

### 5.2 Token Claims

Tokens carry application-specific claims such as:

- `user_id`
- `login_id`
- `user_type`
- `role`
- `full_name`
- `vessel_id`
- `vessel_name`
- `vessel_code`
- `employee_id`
- `crew_id`
- `rank`
- `department`
- `form_ids`
- `process_ids`
- `has_global_vessel_access`

### 5.3 Request Authentication

`PSCJWTAuthentication` reconstructs a lightweight authenticated user object from the JWT claims. This user object is what every permission class reads.

### 5.4 Logout

Logout blacklists the refresh token when possible, but the frontend still clears local auth state regardless of blacklist outcome.

## 6. Permission Model

The backend uses two layers of access control:

1. JWT identity and role claims
2. object-level vessel and workflow permission checks

Role categories:

- vessel roles: `VESSEL_MASTER`, `VESSEL_CREW`
- office roles: `OFFICE_PIC`, `OFFICE_SSQE`, `OFFICE_SUPT`, `DPA`, `PHYSICAL_VERIFIER`

Office visibility is further constrained by vessel assignment unless the user has global access.

## 7. App Responsibilities

### 7.1 `apps/accounts`

- login/logout/me endpoints
- crew lookup

- custom authentication backend
- token claim generation

### 7.2 `apps/masters`

- follow-up wizard

### 7.4 `apps/car`

- CAR detail and workflow
- evidence
- corrective actions
- physical verification
- PDF export
- activity and audit tracking

### 7.5 `apps/notifications`

- in-app notification listing and mark-read flows

### 7.6 `apps/sync`

- push/pull delta sync
- conflict detection
- attachment upload for offline sync

### 7.7 `modules/circular`

- legacy circular office and ship endpoints
- notification generation, delivery tracking, acknowledgments, PDFs

### 7.8 `modules/orb`

- legacy ORB vessel entry APIs
- operation entry maintenance
- approved/rejected/deleted views

## 8. Error Handling Conventions

- Validation failures return `400` with an `error` code, human message, and details where available.
- Permission failures return `403`.
- Missing records return `404`.
- Unexpected server issues return `500`.

The frontend's API client understands the standard error envelope and surfaces the first validation message when possible.
